# 스트리밍 근사 알고리즘 — Bloom Filter · Count-Min Sketch

대용량 스트림 데이터를 **전체 적재 없이 한 줄씩** 처리하면서, 확률적 자료구조로 집합 포함 여부·빈도를 근사하는 프로젝트다. 정확한 정답(Ground Truth)과 비교해 정확도·메모리·시간 세 축으로 성능을 분석한다.

## 데이터셋

**MovieLens 1M** — 사용자-영화 평점 스트림 (`ml-1m/ratings.dat`)

| 항목 | 값 |
|------|----|
| 레코드 수 | 1,000,209 |
| 형식 | `userId::movieId::rating::timestamp` |
| 예시 | `1::1193::5::978300760` |
| 고유 영화 | 3,706 |
| 파일 크기 | 23.5 MB |

다운로드: https://files.grouplens.org/datasets/movielens/ml-1m.zip

## 파일 구성

| 파일 | 역할 |
|------|------|
| `data_prep.py` | **STEP 01 데이터 준비.** 제너레이터로 한 줄씩 스트림 로드 (메모리 비적재) |
| `bloom_filter.py` | Bloom Filter — 포함 여부 근사 (직접 구현) |

| `analyze.py` | 정확도·메모리·시간 성능 분석 |

## 실행 방법

```bash
python data_prep.py      # 데이터 로드 검증 (총 레코드 수 + 샘플)
python ground_truth.py   # 정답 vs 근사 비교
```

> 모든 코드는 **표준 라이브러리만** 사용한다 (`hashlib`, `math`, `collections`). 알고리즘 패키지(`datasketch`, `pybloom`, `numpy` 등)는 쓰지 않고 핵심 로직을 직접 구현했다.

## 핵심 로직 설명

### 1. Bloom Filter — 원소 포함 여부 근사

- m비트 비트배열과 k개의 해시 함수로 집합을 표현한다.
- **add(x)**: x를 k개 위치에 해시해 비트를 모두 1로 세팅.
- **contains(x)**: k개 위치가 모두 1이면 "있을 수 있음", 하나라도 0이면 "확실히 없음".
- **해시 합성**: SHA-256 한 번으로 `h1`, `h2`를 뽑고 `g_i(x) = (h1 + i·h2) mod m`으로 k개 해시를 만든다(double hashing).
- **보장**: 거짓 음성(있는데 없다고 함)은 절대 없고, 거짓 양성만 발생한다.
- 최적 파라미터: `m = -n·ln(p)/(ln2)²`, `k = (m/n)·ln2`.

### 2. Count-Min Sketch — 항목별 빈도 근사

- d개 행 × w개 열의 정수 카운터 테이블로 빈도를 근사한다.
- **add(x)**: 행마다 해시한 칸을 +1 (행별로 다른 해시 사용).
- **estimate(x)**: 행별 해당 칸 값 중 **최솟값**을 반환 → 충돌로 부풀려진 값을 최대한 제거.
- **보장**: 해시 충돌은 카운터를 키우기만 하므로 과소추정이 없고, 추정값은 항상 실제값 이상이다.
- 파라미터: `w = ⌈e/ε⌉`, `d = ⌈ln(1/δ)⌉`.

### 표준 라이브러리 역할

핵심 알고리즘은 직접 구현했고, 표준 라이브러리는 보조 용도로만 사용한다.

| 라이브러리 | 역할 |
|-----------|------|
| `hashlib.sha256` | 균등 분포 해시값 제공 (여러 독립 해시는 직접 합성) |
| `math` | 최적 파라미터 공식(log, e) 계산 |

## 성능 분석 결과

전체 1,000,209 레코드 기준 (`analyze.py`).

### 정확도

| 알고리즘 | 지표 | 값 |
|---------|------|----|
| Bloom Filter | 거짓음성 / FPR | 0 (보장) / **1.0133%** (이론 상한 1.0152%) |
| Count-Min Sketch | 평균 상대오차 / 최대 절대오차 | **0.0000%** / +0 |

### 메모리 (tracemalloc 실측 피크)

| 알고리즘 | 실제 할당 | 자료구조 | 절약 |
|---------|----------|---------|------|
| Ground Truth | 87.2 MB | set + dict (전체 보관) | — |
| Bloom Filter | 1.2 MB | 비트배열 (m=9.6M, k=6) | **74.6배** |
| Count-Min Sketch | 1.7 MB | 카운터 19만개 (w=27,183, d=7) | **50.4배** |

### 시간

| 알고리즘 | 처리 시간 | 처리량 |
|---------|----------|--------|
| Ground Truth | 15.00 s | 66,697 rec/s |
| Bloom Filter | 45.85 s | 21,817 rec/s |
| Count-Min Sketch | 56.47 s | 17,712 rec/s |

> 메모리는 근사 구조가 50~75배 유리하지만, 시간은 레코드마다 SHA-256을 호출하느라 더 느리다 — **메모리를 아끼는 대가로 CPU를 더 쓰는** 전형적 트레이드오프다.

## 파라미터 비교 실험

샘플 10만 레코드 기준 (`parameter_comparison.py`).

### Bloom Filter — 비트 배열 크기 m (k=6 고정)

| m (bits) | 크기 | FPR(실측) |
|---------|------|----------|
| 200,000 | 24 KB | 73.88% |
| 1,000,000 | 122 KB | 0.83% |
| 5,000,000 | 610 KB | 0.00% |

### Bloom Filter — 해시 개수 k (m=1,000,000 고정)

| k | FPR(실측) |
|---|----------|
| 1 | 9.30% |
| 6 | 0.83% |
| **8** | **0.79%** (최저) |
| 16 | 2.70% |

→ 이론 최적 k(≈6.9)에서 FPR이 최저, 넘으면 비트 과포화로 다시 증가한다.

### Count-Min Sketch — width w (d=5 고정)

| w | 평균 상대오차 |
|---|-------------|
| 50 | 29,059% |
| 2,000 | 62.4% |
| 10,000 | 0.0009% |

### Count-Min Sketch — depth d (w=200 고정)

| d | 평균 상대오차 |
|---|-------------|
| 1 | 9,488% |
| 8 | 4,488% |

→ width가 depth보다 정확도에 훨씬 큰 영향을 준다 (충돌 자체를 줄이는 건 w).
